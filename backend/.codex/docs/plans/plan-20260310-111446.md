## Objective
- Make `user_manager` and `security_officer` fully valid backend API roles wherever membership roles are accepted or exposed in this repo.
- Remove temporary schema/test guardrails that still treat the new roles as hidden or invalid.
- Keep backend and frontend aligned by publishing a stable backend contract the frontend issue can consume.

## Scope Guardrails
- In scope: OpenAPI source schemas, bundled OpenAPI artifacts, request validation coverage, membership/session/billing role response schemas, role fixtures, and tests that explicitly exclude or reject the new roles.
- Out of scope: frontend code changes in `vilocify-frontend`, RBAC redesign, permission-model changes, invitation business-rule changes, or dropping git stashes during planning.
- Assumptions:
  - The current issue supersedes the scout's March 2 decision that kept `user_manager` non-submittable in request schemas.
  - Request and response role values should match runtime enum identifiers exactly.
  - Any role-bearing response schema left unchanged is a bug, even if not named explicitly in the AC.

## Known / Inferred / Unknown
### Known
- Runtime already supports both roles in PostgreSQL and ActiveRecord enum mapping (`db/schema.rb`, `app/models/membership/authorization.rb`).
- Request validation is contract-driven via `RequestSchemaValidation` and OpenAPI source files.
- `test/integration/api/v2/memberships_controller_test.rb` still asserts `security_officer` is blocked by schema validation.
- `test/integration/api/v2/sessions_controller_test.rb` still excludes `user_manager` and `security_officer` from role conformance coverage.
- Membership fixtures currently contain only `admin` and `user`.

### Inferred
- Once fixtures for the new roles exist, any unpatched role-bearing response schema can fail `assert_api_conform`.
- The postponed stash work is best treated as evidence of intended cleanup areas, not as source-of-truth code to copy blindly.

### Unknown
- None that still block implementation planning in this repo.

## Architectural Change Model
- Keep the existing runtime flow intact: controller logic, authorization scopes, serializers, and invitation jobs do not change behaviorally.
- Change the API contract to catch up with runtime by making OpenAPI the same source of truth for the expanded role set.
- Use one shared OpenAPI schema for membership role values and reference it from membership/session/billing response schemas and request/filter definitions, so future role additions do not require another sweep of duplicated enums.

## Before / After
**Before**
- Runtime accepts and emits `user_manager` / `security_officer` in parts of the app, but request validation and OpenAPI docs still lag behind.
- Membership create request schemas and membership role filters allow only `admin` / `user`.
- Session conformance coverage intentionally excludes the new roles.
- Fixtures and serializer tests barely exercise the new roles.

**After**
- OpenAPI request validation accepts all four membership roles where membership roles are valid input.
- Membership, session, and billing role responses document the full runtime role set using `snake_case`.
- Tests use fixtures for `user_manager` and `security_officer` instead of excluding them.
- Bundled public/internal OpenAPI artifacts match the updated source contract.

## Execution Flow: Current vs New
### Current
1. `POST /memberships` request hits `RequestSchemaValidation`.
2. OpenAPI request schema rejects `user_manager` / `security_officer` before controller logic runs.
3. `GET /sessions` and `GET /sessions/current` can serialize runtime role values, but conformance tests avoid exercising the new ones.
4. `assert_api_conform` validates responses against stale bundled schemas that only know two roles.

### New
1. `POST /memberships` request hits updated OpenAPI schemas and accepts all four role identifiers.
2. `MembershipsController#create` continues using the same authorization/runtime path, now reachable for the new roles.
3. Session, membership, and billing responses remain serialized with runtime role values, now backed by matching OpenAPI enums.
4. Fixture-driven integration and serializer tests exercise all four roles, so conformance failures surface immediately if a schema drifts again.

### Deltas
- Contract gate changes from "hide new roles" to "accept and document new roles".
- Conformance strategy changes from manual exclusion to positive coverage.
- Role enum duplication is reduced by introducing a shared OpenAPI role schema.

## Loop Closure
- Trigger: membership/session/billing endpoints are called with or return `user_manager` / `security_officer`.
- Completion signal: request validation accepts those roles, the response validates cleanly against OpenAPI, and focused tests pass without role exclusions.
- Failure signal: any 422 still listing only `admin`, `user`; any conformance failure for session/membership/billing responses; or any remaining test explicitly excluding the new roles.

## Implementation Steps
1. Add a shared OpenAPI membership-role schema containing `admin`, `user`, `user_manager`, `security_officer` in `snake_case`.
2. Replace inline membership-role enums in membership create/filter and membership/session/billing response schemas with that shared schema, keeping nullable session role definitions as `oneOf: [role-ref, null]` where needed.
3. Rebundle OpenAPI so `public/openapi/v2.yml` and `public/openapi/internal.yml` match the source docs.
4. Add accepted membership fixtures for `user_manager` and `security_officer`.
5. Update request validation tests to reflect the expanded allowed-value set and add/confirm successful membership create request coverage for the new roles.
6. Remove obsolete “blocked by schema validation” and role-exclusion tests; replace them with positive fixture-driven coverage in memberships, sessions, serializers, and any billing conformance surface that emits roles.
7. Run focused OpenAPI + API test commands, then widen only if the focused run reveals another role-bearing surface that still drifts.
