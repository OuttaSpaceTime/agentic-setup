# Guided Scout: API v2 Announcements Endpoint

## Checkpoint 1/6: Problem Frame

Context gathered:

- Announcements already exist in the app, but only as stored records plus an email-delivery flow.
- There is no current frontend-readable API endpoint for announcements.
- Internal endpoints already have a clear repo pattern: session auth, internal docs, no public bearer-token exposure.

Walkthrough Evidence

- evidence type: `requirement`
- location: user-provided ticket text
- evidence path: acceptance criteria -> endpoint + filtering + docs + auth
- short excerpt:
  - "Create a new `/api/v2/announcements` endpoint"
  - "Only announcements where its publish_date is in the past"
  - "Only the 3 latest published announcements"
  - "HTML generated from the saved markdown"
  - "You can access this endpoint if you're logged in, no additional permission required"
- interpretation:
  - This is a read-only internal frontend feed, not a general public API resource.
- unknowns:
  - whether `title` belongs in the response
  - whether deleted announcements must remain hidden
  - exact publish-date field naming

Checkpoint outcome:

- Include `title`
- Exclude deleted announcements

## Checkpoint 5/6: Risk and Verification

Risk 1:

- The existing `Announcement.published` scope is shared with delivery logic.
- If implementation changes that scope to include same-day announcements, email timing changes too.

Walkthrough Evidence

- evidence type: `decision gate`
- location: `app/models/announcement.rb:5`, `test/models/announcement_test.rb:20`
- evidence path: `app/models/announcement.rb:5 -> test/models/announcement_test.rb:20`
- short excerpt:
  - `published` currently means `< Date.current`
  - tests already assert future-dated announcements are not sent
- interpretation:
  - visibility changes can have side effects outside the new endpoint
- unknowns:
  - none after scout; keep API behavior consistent with current mail behavior

Risk 2:

- The generic API collection serializer expects pagination links.
- A fixed latest-3 feed may not fit the normal `serialize_collection` path cleanly.

Walkthrough Evidence

- evidence type: `behavior trace`
- location: `app/controllers/concerns/api_serialization.rb:6`, `lib/action_json_api/base_controller/pagination_links.rb:4`, `app/models/concerns/json_api_pagination.rb:23`
- evidence path: `app/controllers/concerns/api_serialization.rb:6 -> lib/action_json_api/base_controller/pagination_links.rb:4 -> app/models/concerns/json_api_pagination.rb:23`
- short excerpt:
  - `serialize_collection` calls `build_pagination_links(collection.links)`
  - `build_pagination_links` assumes `links.transform_values`
  - paginated collections normally come from `json_api_sort_and_paginate`
- interpretation:
  - implementation should likely use a custom collection serialization path for this fixed feed
- unknowns:
  - none at scout level; this is an implementation-shape caution

Verification path:

- add endpoint integration tests for auth and visibility
- expand fixtures for limit/order coverage
- validate response against internal OpenAPI spec
