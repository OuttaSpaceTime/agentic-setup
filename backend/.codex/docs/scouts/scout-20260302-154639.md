## Execution Flow: Current vs Planned
### Current Flow
1. `POST /memberships` calls `authorize!(Membership)` (write scope) and passes if writable scope is non-empty.
2. Controller persists membership with `role: invitation_params[:role]` directly.
3. `after_create` enqueues Siemens invitation job.
4. `PATCH /memberships/:id` loads writable-scoped record and updates `expiresAt` only.

### Planned Flow
1. Role model includes `user_manager` as persisted role (display label: `User Manager`).
2. `POST /memberships` uses `allowed?(Membership.editable_for_invitation(target_role))` for permission + target-role gating in one model scope path.
3. `PATCH /memberships/:id` uses `allowed?(Membership.where(id: params[:id]).editable_for_expiration)` to load only expirably-editable targets.
4. `PATCH` still enforces simple block semantics in model scope logic (e.g. Security Officer/Admin blocked unless full write permission).
5. OpenAPI request schema keeps `role` enum without `user_manager`, so API clients cannot submit `user_manager` as invite target for now.
6. Contracts and tests are updated to remain consistent with this rollout constraint.
7. Hidden/non-selectable manager behavior is handled in later cleanup issue.

### Flow Deltas
- Authorization shifts from permission-only to permission + role-target rule checks.
- Membership create/update no longer rely on generic `Membership.editable`; they rely on purpose-specific scopes via `allowed?`.
- Role enum becomes broader internally and contractually for this ticket.
- Deferred cleanup will later tighten external exposure/selectability behavior.
