# Scout Brief: Org Expiry Emails Send Wrong Expiry Date

## Source Request
- Issue: "Org Expiry Emails send out the wrong expiry date"
- Expected behavior: if an organization has a current period and a future follow-up period, the reminder email should show the organization's final expiry date, not the current active period end.

## Fast Context Map
- Reminder entrypoint: `app/models/task/organization_expiries_reminder.rb`
- Mail assembly: `app/mailers/organization_expiries_mailer.rb`
- Rendered body: `app/views/organization_expiries_mailer/admin_reminder.html.erb`
- Expiry selection logic: `app/models/organization/expiry.rb`
- Existing coverage: `test/models/task/organization_expiries_reminder_test.rb`, `test/mailers/organization_expiries_mailer_test.rb`

## Current Behavior Trace
1. `Task::OrganizationExpiriesReminder.send_admin_expiry_reminders!` selects organizations whose maximum consumption-period end falls within the reminder windows.
2. For each admin, `OrganizationExpiriesMailer.admin_reminder` loads `@organization = @recipient.organization`.
3. The email body renders `@organization.current_consumption_period.period.end`.
4. For overlapping or back-to-back periods, step 1 uses the furthest period end, but step 3 uses only the active period end.

## Known Facts
- Reminder eligibility already keys off the maximum consumption-period end date.
- The bug is in email rendering, not reminder targeting.
- A model-level helper is the cleanest place to unify the expiry definition.

## Hypotheses
- Adding `organization.expiry_date` (or equivalent) and using it in the template will close the inconsistency with minimal blast radius.

## Unresolved Unknowns
- None blocking for this issue.

## Decision Gates
- Acceptance/business rule: use the furthest consumption-period end as the organization expiry shown in reminder mails.
- Minimal-first scope: patch model + template + regression test only.
- Test proof: add overlapping-period mailer coverage and rerun focused tests.
