# Scout: API v2 Announcements Endpoint

## Source Request

Issue summary:

- Create a new `/api/v2/announcements` endpoint that returns a new announcements resource
- Only announcements where its publish_date is in the past are part of the response
- Only the 3 latest published announcements are exposed
- Add the endpoint to the internal documentation
- The resource should display:
  - HTML generated from the saved markdown
  - Created and Updated at timestamps
  - The publish date
- You can access this endpoint if you're logged in, no additional permission required

Captured scout decisions:

- Include `title` in the response
- Exclude deleted announcements
- Keep publish visibility consistent with current mail behavior
- Use `publishOn` as the date field name
- Keep the endpoint a fixed latest-3 feed, not a paginated general list

## Current Code Walkthrough

### 1. API entrypoint pattern

Internal frontend endpoints live under `api/v2`, are constrained to JSON:API requests, and commonly use a dedicated session-only auth macro rather than bearer-token or permission-scoped public API behavior.

Evidence:

- `config/routes.rb:58` defines the `api/v2` namespace under `constraints(format: :jsonapi)`
- `app/controllers/api/v2/user_settings_controller.rb:3` uses `only_session_auth_for_internal_endpoints!`
- `app/controllers/concerns/authentication.rb:16` implements that macro by enforcing `authenticate_with_session!`

Interpretation:

- The new endpoint should follow the internal endpoint pattern, not the public API-token pattern.

### 2. Announcement domain behavior

Announcements already exist as persisted records with fields needed by the frontend plus email-delivery-specific fields.

Evidence:

- `db/schema.rb:59` defines `title`, `markdown`, `publish_on`, `created_at`, `updated_at`, `deleted`, `enqueued_at`
- `app/models/announcement.rb:5` defines `published` as `publish_on < Date.current`
- `app/models/announcement.rb:8` defines delivery scope as `not_deleted.published.sends_out_mail.not_sent`

Interpretation:

- There is already a domain concept of visibility.
- Deleted announcements are already treated as hidden in the mail-delivery flow.

### 3. Markdown-to-HTML behavior

The app already has one canonical announcement markdown renderer and it is already exercised by tests.

Evidence:

- `app/helpers/markdown_helper.rb:30` exposes `markdown_to_html`
- `app/views/announcement_mailer/notification.html.erb:1` renders announcement markdown with that helper
- `test/helpers/markdown_helper_test.rb:4` and `:51` pin both normal rendering and sanitization behavior

Interpretation:

- The API should reuse the existing renderer instead of introducing a second markdown pipeline.

### 4. Internal documentation behavior

Internal endpoints are documented in the split OpenAPI spec and marked with `x-internal`.

Evidence:

- `openapi/openapi.yml:14` marks internal endpoints with `x-internal`
- `openapi/tags.yml:1` marks internal tags with `x-internal`
- `Readme.md:158` explains that `?name=internal.yml` exposes internal docs

Interpretation:

- The new endpoint belongs in internal documentation only.

## Known Facts, Hypotheses, Unknowns

Known facts:

- The endpoint is internal and session-cookie-based by convention.
- The resource must include rendered HTML, timestamps, and a publish date.
- The repo already contains the announcement domain and markdown renderer.

Hypotheses confirmed during scout:

- The response should also include `title`.
- Deleted announcements should be hidden.
- `publishOn` is the right response field name because existing date-only API fields use `...On`.

Unknowns resolved during scout:

- Same-day `publish_on` handling:
  - Final direction: keep behavior consistent with current mail behavior.
  - Meaning: on March 19, 2026, only announcements with `publish_on` on March 18, 2026 or earlier are visible.
- Endpoint shape:
  - Final direction: fixed latest-3 feed.
  - No general pagination/sort/filter behavior is required for v1.

## Decision Gates

### Gate 1: Internal vs public endpoint

- Decision: internal endpoint
- Alternatives considered: public bearer-token endpoint
- Rationale: acceptance criteria explicitly say "logged in" and docs should be internal; repo already has a session-only pattern
- Confidence: high
- Required now: yes

### Gate 2: Publish visibility rule

- Decision: match current mail behavior
- Alternatives considered: same-day inclusion
- Rationale: keeps frontend visibility consistent with current announcement publication semantics
- Confidence: high
- Blockers: none
- Required now: yes

### Gate 3: Scope boundary of list behavior

- Decision: fixed latest-3 feed
- Alternatives considered: generic list with sorting/pagination
- Rationale: acceptance criteria already hard-code visibility and count; broader list behavior is extra scope
- Confidence: high
- Blockers: none
- Required now: yes

### Gate 4: Deleted rows

- Decision: exclude deleted announcements
- Alternatives considered: expose deleted rows if publish rule matches
- Rationale: current domain semantics already treat deleted announcements as hidden
- Confidence: high
- Blockers: none
- Required now: yes

### Gate 5: Publish date field naming

- Decision: `publishOn`
- Alternatives considered: `publishDate`
- Rationale: matches existing date-only naming patterns such as `expiresOn` and `thirdPartyPublishedOn`
- Confidence: medium-high
- Blockers: none
- Required now: yes

## Current vs Planned Execution Flow

Current flow:

1. Announcements are created/edited through CLI/admin workflow.
2. Visibility for mail delivery is determined by `Announcement.not_deleted.published.sends_out_mail.not_sent`.
3. Markdown is rendered in the mailer view through `markdown_to_html`.
4. There is no frontend-readable API endpoint for announcements.

Planned flow:

1. Logged-in frontend calls `GET /api/v2/announcements`.
2. Controller authenticates through session-only internal endpoint behavior.
3. Controller loads the latest 3 non-deleted announcements whose `publish_on` is before the current day.
4. Serializer exposes `title`, rendered HTML, `publishOn`, `createdAt`, and `updatedAt`.
5. OpenAPI internal docs document the endpoint.

Delta points:

- New read path for data that previously existed only in persistence + mail delivery
- New API contract for rendered HTML
- New internal-doc exposure

## Risk, Compatibility, Security

Compatibility assessment:

- Auth surface: compatible
  - uses existing internal session-only pattern
- Documentation surface: compatible
  - internal-only OpenAPI update
- Announcement delivery behavior: conditional
  - only if implementation incorrectly changes shared `published` scope
- Frontend contract: additive
  - brand-new endpoint

Security assessment:

- No new write surface
- HTML content remains derived from the existing sanitized renderer
- Endpoint should not accept API tokens if it follows internal endpoint conventions

Key mitigations:

- Keep API visibility logic separate from any mail-delivery scope changes unless deliberately intended
- Reuse existing markdown renderer
- Test unauthenticated, partially authenticated, and API-token request behavior explicitly
