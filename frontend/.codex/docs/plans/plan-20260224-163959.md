## Objective
- Align permission handling with `origin/main` architecture while preserving your directive API direction:
  - no ML-specific permission directives,
  - no signal-based permission directives,
  - synchronous session checks in directives,
  - ML editability resolved in component observables and passed as booleans.

- In scope: rebase onto `origin/main`; remove ML directives; remove `authorization.service.ts`; introduce/keep three generic directives; refactor ML role propagation to detail-scoped observable service (`role$ + setRole`).
- In scope: migrate monitoring-list templates/components from ML directives to boolean inputs and `async`-driven conditions.

## Before / After
**Before**
- Branch introduces async signal-based permission directives (`has-ml`, `readonly-ml`, `disabled-ml`) and `AuthoriziationService`.
- Branch adds caching/invalidation behavior to root `SubscriptionRoleService`.
- `origin/main` has major service/client refactors and component-level permission booleans for ML tabs.

**After**
- Rebased code keeps `origin/main` service/client architecture.
- Exactly three generic permission directives remain, all using sync session snapshot checks.
- ML permission decisions happen in components (`Observable<boolean>` + `async`), no ML directives.
- Detail-level role state service (`role$ + setRole`) is provided at detail page level and updated after subscription mutations.

## Execution Flow: Current vs New
### Current
1. Components bind ML configs into `appHasMLPermission` / `appReadonlyMLPermission` / `appDisabledMLPermission`.
2. Directives call async resolver service to combine session + fetched subscription role.
3. `SubscriptionsService` mutation hooks invalidate cached role service globally.

### New
1. Detail root provides current ML subscriber role stream service instance.
2. Tabs derive `canEdit$` from `session$` + `role$` + monitoring-list model rules.
3. Templates use `@if`/`async` or generic directives with boolean input.
4. Subscription create/update/delete pushes new role via `setRole` (and tab recomputes instantly).
5. Generic directives evaluate synchronously from `AuthenticationService.currentSession` and/or boolean input.

### Deltas
- Removes resolver indirection and ML-specific directives.
- Moves ML role responsibility from directive internals to detail component composition.
- Replaces global cache-key invalidation semantics with detail-scoped explicit updates.

## Implementation Steps
1. Rebase `513-permission-directives` on `origin/main`.
2. During conflict resolution, for service/client refactor conflicts keep `origin/main` versions (drop branch service-layer variants as requested).
3. Delete `authorization.service.ts` and all imports/usages.

5. Keep/refine `appHasPermission` with `RequiredPermission | boolean` sync checks against `currentSession`.
6. Refactor `appReadonlyPermission` to sync style (no `signals`, no resolver).
7. Add `appDisabledPermission` generic sync directive (permission or boolean + explicit `[disabled]` override precedence).
8. Refactor monitoring-list detail tabs/components/templates to pass ML booleans from observable pipelines (`async`) instead of ML directives.
9. Introduce/refactor detail-scoped current-subscriber-role service (`role$`, `setRole`, optional initial seed), provided only at detail component level.
10. Update subscription mutation flows to push role changes into detail-scoped role stream.
11. Update tests for deleted directives and new generic/directive/component contracts.
12. Run lint/tests and fix regressions.

## Decision Update (Latest)
- Remove all permission base directives entirely (e.g. `ReadonlyBaseDirective`, `PermissionViewBaseDirective`).
- Concrete directives (`appHasPermission`, `appReadonlyPermission`, `appDisabledPermission`) must be self-contained and synchronous.
- No abstract/shared directive base class layer remains under `src/app/shared/directives/permissions/base`.

## Decision Update (Inputs + Precedence)
- No `input()` signal inputs in directives; use classic `@Input(...)` only.
- `appDisabledPermission` and `appReadonlyPermission` precedence rule:
  - effective state is permission gate OR explicit UI state.
  - `disabled = permissionDenied || explicitDisabled`
  - `readonly = permissionDenied || explicitReadonly`
  - Explicit `true` may further restrict.
  - Explicit `false` never grants access if permission denies.
- For ML cases, components pass boolean values derived from role/session observables (via `async`) to generic directives or `@if` blocks.
