# Implementation Plan: Inbox Page Scaffold

Mode: Scout-backed planning

Source request:

- Implement the Inbox Page Scaffold.
- First pass is shell, bare routing, and resolver only.
- Mock service is only for initial page load.
- Everything else is mock components with projected content and route logic.
- Route blocking uses `canMatch`.

## Objective

Add a new `/inbox` entry point that can be shown in dev/staging, loads its initial state before activation, and renders a first-pass inbox shell without introducing backend coupling.

## Scope Guardrails

In scope:

- new inbox route
- `canMatch` environment blocking
- route resolver for initial load state and page setup
- shell layout for the inbox page
- mock components / projected content for list and detail placeholders
- navigation entry if needed for discoverability in non-prod

Out of scope for this pass:

- real inbox API integration
- read/unread mutation behavior
- refresh and pagination semantics beyond shell wiring
- mobile modal details beyond shell structure

## Current Flow

1. The app lazy-loads `notifications` from `src/app/app.routes.ts`.
2. The notifications feature renders either the list page at `''` or the routed detail page at `:id`.
3. The existing list/detail experience relies on request-state spinners and a live `NotificationsService`.
4. The sidebar only knows how to hide items through permission/login/dev-mode checks.

## Planned Flow

1. The app lazy-loads `inbox` from `src/app/app.routes.ts`.
2. A `canMatch` guard blocks the route outside dev/staging.
3. The inbox route resolver loads the initial mock inbox state before activation.
4. The inbox shell reads resolved data and renders the first-pass list/detail layout.
5. Child mock components receive projected content from the shell and provide the visible page structure.

## Impact Inventory

### `src/app/app.routes.ts`

- Current responsibility: top-level feature route registration.
- Why impacted: add `/inbox` lazy-load entry.
- Change intent: register the new inbox feature module.
- Risk: low.

### `src/app/features/inbox/*`

- Current responsibility: none, new feature area.
- Why impacted: host the shell, route config, resolver, and mock components.
- Change intent: keep inbox logic isolated from the existing notifications feature.
- Risk: medium, because this is a new feature boundary.

### `src/app/core/layout/components/sidebar/sidebar.component.ts` and `.html`

- Current responsibility: top-level navigation and visibility rules.
- Why impacted: expose inbox only in dev/staging if we want it discoverable in the menu.
- Change intent: add one gated entry or equivalent visibility logic.
- Risk: low.

### `src/app/core/services/development.service.ts`

- Current responsibility: environment detection.
- Why impacted: `canMatch` and sidebar visibility can reuse the existing dev/staging checks.
- Change intent: likely no change unless a shared predicate/helper is worth extracting.
- Risk: low.

### `src/app/shared/spec/*` and inbox feature specs

- Current responsibility: test helpers and component specs.
- Why impacted: add route and shell verification.
- Change intent: cover route blocking, resolver behavior, and first-pass shell rendering.
- Risk: low.

## Implementation Steps

1. Create a new inbox feature folder with a route config, shell component, resolver, and mock placeholder components.
2. Add the `/inbox` lazy route in `src/app/app.routes.ts`.
3. Add a `canMatch` gate that allows only dev or staging environments.
4. Implement the inbox resolver so the initial page load is resolved before activation.
5. Render the shell with projected content placeholders for list and detail areas.
6. Add or update the sidebar entry if the first-pass UX should expose the route in non-prod navigation.
7. Add focused route and shell specs.

Focused tests to add or update:

- inbox route spec: asserts `canMatch` blocks unsupported environments
- inbox resolver/spec: asserts initial mock data is resolved before the shell renders
- inbox shell spec: asserts the shell renders projected content and the expected layout state
- sidebar spec if the inbox menu entry is added

Finish signal:

- `/inbox` is reachable in dev/staging
- `/inbox` is blocked outside dev/staging
- the inbox shell renders without a loading spinner flash on first activation
- specs and validation commands pass cleanly

## Compatibility and Risk

- Route behavior: compatible if the new route is isolated and gated with `canMatch`.
- Existing notifications flow: compatible because no existing route is being repurposed.
- Layout behavior: conditional, because the shell may need a small shared pattern if its split-pane structure differs from current `PaneLayoutComponent`.
- Data behavior: compatible for the first pass because the mock service is only used for initial load.

Main risk:

- Overfitting the shell to later data behavior. Keep the first pass limited to route loading, shell composition, and projected placeholders so the mock service does not leak into the rest of the design.
