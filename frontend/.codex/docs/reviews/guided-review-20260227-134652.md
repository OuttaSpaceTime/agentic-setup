## Checkpoint 2: Architecture and Design Decisions
- Key decision 1: move session initialization to app bootstrap (`provideAppInitializer`) and keep current session in a single mutable service.
- Key decision 2: remove async guard/session fallback logic and use direct synchronous property reads.
- Why it matters: this reduces boilerplate but removes built-in timeout/error fallback behavior unless replaced explicitly.

### Code Outline 2.1
- Symbol: `class` `CurrentSession`
- Location: `src/app/core/auth/services/authentication/current-session.service.ts:9`
- Why it matters: defines the new global session contract all guards/components now depend on.

```ts
export class CurrentSession {
  private lastRefreshAt = null
  private currentSession$ = new BehaviorSubject<Session>(null)

  public setCurrentSession(session: Session) {
    this.lastRefreshAt = Date.now()
    this.currentSession$.next(session)
  }

  public get currentSession() {
    return this.currentSession$.value
  }

  isStale() {
    const now = Date.now()
    const delta = this.lastRefreshAt === null ? null : now - this.lastRefreshAt
    return delta > 30_000
  }
}
```

- Interpretation: the service begins with `null` session and considers `null` age as non-stale, so consumers must handle null explicitly or refresh will not self-heal after startup misses.

## Checkpoint 4: Control-Flow Deep Dive
- Happy path: `bootstrap -> fetch session -> setCurrentSession -> guards read login state -> route loads -> layout set -> page renders`.
- Edge/error path: `bootstrap fetch fails -> null session remains -> guard/template dereference -> runtime failure`.
- Additional edge path: `nested child route -> deepest child lacks currentLayout -> root switch gets undefined -> shell not rendered`.

### Code Outline 4.1

## Checkpoint 5: Implications and Breakage Risk
- Possible breakages:
  - blank-screen shell for nested routes with missing child layout data.
  - route guard/runtime exceptions on null session after startup failure.
  - expected client errors (4xx) unexpectedly routed to global `/500`.
- Backward compatibility status: **conditional to breaking** for routing/error UX behavior.
- Test confidence and gaps: suite is green, but missing tests allowed these regressions through.

### Code Outline 5.1
- Symbol: `function` `redirectOnServerError`
- Location: `src/app/core/interceptors/redirect-on-server-error.interceptor.ts:8`

```ts
export const redirectOnServerError: HttpInterceptorFn = (request, next) => {
  const withCustomErrorHandling = request.context.get(CUSTOM_ERROR_HANDLING)

  if (withCustomErrorHandling) {
    return next(request)
  } else {
    return next(request).pipe(
      timeout(10_000),
      catchError((error) => {
        router.navigateByUrl(navigationService.to500(), {
          onSameUrlNavigation: 'reload',
        })
        return throwError(() => error)
      }),
    )
  }
}
```

- Interpretation: every unhandled error now triggers `/500`, including non-server 4xx cases where local UX was previously expected.
