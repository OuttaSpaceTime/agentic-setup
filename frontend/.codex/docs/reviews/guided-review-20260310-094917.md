## Checkpoint 4/6: Assumptions and Review Questions

Observed assumptions:

- The settings backend is reachable through `/api/v2/userSettings` or a compatible alias.
- `show('')` is accepted by the backend even though it produces a different path shape than the PATCH.
- Request failures can be safely represented by rendering the toggle without confirmed data.
- A root-scoped, one-shot fragment snapshot is sufficient for settings deep links.

Unresolved review questions:

- Is the canonical API path `/api/v2/settings` or `/api/v2/userSettings`?
- Should failed loads block interaction or surface an explicit error state?
- Must repeated `#settings` links reopen the overlay during the same session?

## Checkpoint 6/6: Tests, Compatibility, Operations, and Verdict

Tests and coverage notes:

- The newly added focused specs pass.
- The current specs validate fragment consumption and initial sidebar state, but they do not assert the actual HTTP URLs or the UI behavior on failed reads/writes.

Compatibility and production-safety notes:

- API compatibility: conditional. The frontend code currently assumes an endpoint shape that is not internally consistent between GET and PATCH.
- UX resilience: weak. Failed reads are shown as a real toggle state instead of an explicit error state.
- Link resilience: conditional. Deep-link behavior depends on first-load timing because the fragment handling is memoized in a root singleton.

Verdict:

- Not merge-ready yet.

Suggested next deep dives:

- Add an HTTP-level spec for `UserSettingsHttpService` to lock the canonical GET/PATCH URLs.
- Decide whether the settings deep link must be first-load-only or reusable during the same session.
- Add an explicit error/retry state for the initial settings fetch.
