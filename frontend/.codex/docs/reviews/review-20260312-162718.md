## Change Approach

The implementation centralizes membership-role metadata in one feature-level definition and then uses that shared source in three places:

1. role publication
   - invite dropdown
   - memberships filter dropdown and validator
   - subscriber/session/billing/card display labels
2. permission scoping
   - invite affordances are gated by invite permissions
   - expiry affordances are gated by per-role expire permissions
3. type widening
   - shared role unions and create-request attributes now accept all published roles

## Execution Flow

### Invite flow

1. Memberships page renders the invite button only when the session has at least one invite permission.
2. Clicking the button opens the modal and instantiates the invite form.
3. The invite form filters `MEMBERSHIP_ROLE_DEFINITIONS` by `currentSession.hasPermission(invitePermission)`.
4. The resulting list becomes the dropdown options and default role.
5. Submit still sends backend enum values unchanged.
6. Success toast uses shared role labels instead of raw snake_case.

### Expiry flow

1. Each membership card renders `app-expiry-input-tag` for the viewed membership.
2. `ExpiryInputTagComponent` derives the required permission from `membership.role`.
3. The template uses `*appShowForPermission="expiryPermission; else readonlyExpiryDisplay"`.
4. `canEditMembership` mirrors that same per-role permission in component logic.
5. Users with invite-only permissions get a read-only display.
6. Users with matching expire permission can open the modal and update expiry.

### Shared role-label flow

1. `membershipRoleLabel()` maps backend values to human labels.
2. Session, menu avatar, membership cards, subscriber cards, subscription form items, and billing tables consume that same mapping.
3. This removes the prior `titlecase` behavior that would have rendered `security_officer` / `user_manager` incorrectly.

## Strengths

- The permission split uses the existing `appShowForPermission` directive instead of hand-rolled conditionals, which keeps the solution aligned with the local authorization pattern.
- Shared role metadata prevents the same four-role definition from drifting across invite UI, expiry logic, filters, and label formatting.
- The implementation widened the type surface as well as the UI surface, reducing the chance of future `admin | user` regressions hiding in request types or model attributes.
