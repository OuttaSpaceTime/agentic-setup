## Change Approach

The implementation centralizes role metadata in one shared module, then fans that metadata into:

- invite role option generation
- memberships filter options and validation
- per-membership expiry authorization
- shared role-label rendering across session, memberships, subscriber, and billing surfaces

Authorization is split on the intended UI seams:

- route/sidebar/page access still use the combined membership-write permission family
- the invite affordance is narrowed to invite permissions
- expiry editing is narrowed to the exact role-specific expiry permission

## Execution Flow

### Invite flow

1. Memberships route remains guarded by `requiresAtLeastOnePermission(...MEMBERSHIP_WRITE_PERMISSIONS)`.
2. Memberships page renders the invite button only when `*appShowForPermission="MEMBERSHIP_INVITE_PERMISSIONS"` passes.
3. Invite modal opens the invite form.
4. Invite form derives `selectItems` by filtering the shared role definitions through `currentSession.hasPermission(invitePermission)`.
5. Submission still posts the backend enum role unchanged.

### Expiry flow

1. Membership card renders `app-expiry-input-tag` for each membership.
2. Expiry input resolves the viewed membership role into one exact expiry permission.
3. The template uses `*appShowForPermission="expiryPermission; else readonlyExpiryDisplay"`.
4. The runtime guard in `openExpiryPickerModal()` also checks `canEditMembership`.
5. Successful expiry updates still refresh the session.

### Role-label publication flow

1. Shared metadata defines the canonical label once.
2. `membershipRoleLabel(...)` is reused in session model getters and component class helpers.
3. `MembershipRoleLabelPipe` makes the same mapping available in templates.
4. `CardTitleComponent` now supports preformatted detail strings without forcing `titlecase`.
